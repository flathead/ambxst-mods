Архитектура календарной интеграции

Два подхода к взаимодействию QML ↔ Calendar API

A

Единый Python-процесс (рекомендую)

Один долгоживущий Python-скрипт — по аналогии с system_monitor.py

┌─────────────────────────────────┐
│ QML (CalendarService.qml) │
│ Singleton, как SystemResources │
└──────────┬──────────────────────┘
│ stdin: команды (JSON)
│ stdout: данные (JSON lines)
┌──────────▼──────────────────────┐
│ Python (calendar_service.py) │
│ OAuth, CalDAV, кэш, notify │
└──────────┬──────────────────────┘
│ HTTP/CalDAV
┌──────────▼──────────────────────┐
│ Google Calendar API / CalDAV │
└─────────────────────────────────┘
+ Знакомый паттерн (system_monitor.py)
+ Богатые Python-библиотеки (google-api-python-client, caldav, icalendar)
+ Один процесс = проще управлять
+ stdin/stdout для двусторонней связи (команды от QML → ответы от Python)
− Один скрипт отвечает за всё (OAuth + sync + cache + notify)
B

Разделённая архитектура: Sync + Cache

Python-скрипт для синхронизации, FileView для кэша

┌─────────────────────────────────┐
│ QML (CalendarService.qml) │
│ Читает кэш через FileView │
└────┬─────────────────┬──────────┘
│ FileView │ Process (команды)
┌────▼────┐ ┌───────▼──────────────┐
│ JSON │ │ Python (calendar_sync) │
│ cache │◄───│ OAuth, CalDAV, CRUD │
└─────────┘ └───────┬──────────────┘
│ HTTP/CalDAV
┌───────▼──────────────┐
│ Google / CalDAV │
└──────────────────────┘
+ Разделение ответственности: sync отдельно, кэш отдельно
+ FileView автоматически реагирует на изменения файла
+ Процесс запускается только для команд, не живёт постоянно
− Два механизма связи (FileView + Process) сложнее
− Гонки при одновременном чтении/записи кэша
− Уведомления требуют отдельного таймера/процесса
